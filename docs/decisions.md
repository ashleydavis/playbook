# Decisions

A chronological log of decisions about the Playbook process: what changed and why. Newest first. Each entry has a date, a one-line title, and a short "what / why" body. This is not a queue or a status file and it never tracks in-flight work; for that, run `/pb:status` (which summarises the live ticket queues) or `/pb:board`.

## 2026-07-19: `pb:review` inspects a ticket in its worktree, never `project/`, and a standing rule against guessing

**What changed:** two coupled changes. **(1) The review's runnable and diff actions are bound to the ticket's worktree.** `ticket-card.ts` now resolves the ticket's worktree (`project/worktrees/<id>`), reads its checked-out HEAD, and confirms that HEAD equals the branch tip the card reports as `Commit`. The card prints a `Worktree (run / launch / diff from HERE, never project/):` line when they match, and a loud `** WARNING **` (no silent thinner card) when the worktree is missing or its HEAD does not match. `pb:review`'s inspect loop gained a mandatory **Preflight** before options 2, 3, 4, 7, 8: use the worktree path as the working directory / `git -C` target, verify HEAD against the card's commit, and **STOP** (never fall back to `project/`) if the worktree is missing or mismatched. Options 2/3/4 now root their setup/start/test commands at the worktree, and re-read "from the repo root" in a testing manual as "from the worktree". Every such command must pin the directory in the command itself as a subshell (`(cd project/worktrees/<id> && <cmd>)`), never a bare command relying on the session cwd, and the printed description must match the issued command's directory character for character. Before running anything, the agent must **announce the location to the developer** ("I will run the app from <path>"), so a wrong path is caught up front rather than by clicking a broken app. "Start it for you" must **verify the launched app is actually rooted in the worktree** (e.g. the serving process's `/proc/<pid>/cwd`) before handing it over, and kill-and-stop rather than hand over an unverified app. Encoded in `scripts/ticket-card.ts` (+ `scripts/ticket-card.test.ts`) and `.claude/commands/pb/review.md`. **(2) A standing anti-guessing rule** was added to `CLAUDE.md`: never state a count, fact, or outcome not verified; say "I don't know" rather than estimate; check a checkable fact before stating it; flag unverified evidence as unverified; and prove you are acting on the thing under review before running/launching/diffing to prove it works.

**Why:** at the human-review gate for `cluster-cache-3` (a refresh-button fix, already human-rejected three times), the developer picked "Start it for you" and I launched `bun run dev` from `project/`, which is on `main`. `main` does not contain the ticket's fix (it lives only in the unmerged worktree `project/worktrees/cluster-cache-3`), so the developer clicked refresh, saw the original bug, and rejected again, this time on code that was never the code under review. The whole purpose of the review gate is to inspect unmerged work, which by definition lives on a branch/worktree, yet nothing in the flow pinned the app to that worktree: the testing manual says "from the repo root" (written for a developer on `main`), the skill reused those commands verbatim, and I ran them without the one check the review exists to perform, that the running code is the ticket's code. The card even carried the commit and the worktree existed; I used neither. Asked afterwards how many times this had happened across sessions, I began to offer an estimate, which is the same failure in another form: stating a number I had not verified. Both faults are the same root, acting on or asserting something without first confirming it is the real thing. The worktree binding makes the wrong-tree launch impossible to do silently (the card names the right tree and the preflight halts on a mismatch); the anti-guessing rule makes "I don't know" the required answer wherever verification is missing.

## 2026-07-17: `pb:review` never asks the developer how they want the screenshots shown

**What changed:** the inspect loop's "Show the screenshots" option now forbids asking the developer anything about how to show them. Picking the option is the whole answer: open every screenshot in the pass, whatever the count. No offering a subset, a "representative sample", light-mode-only, the folder instead of the files, or a menu of those; and no stopping to flag that the count is large. Encoded in `.claude/commands/pb/review.md`.

**Why:** reviewing `timestamp-format-1` (64 screenshots, 16 views x age/local x light/dark), the developer picked option 1 and I asked them how they wanted to see them instead of opening them. The count triggered it: 64 `xdg-open` calls spawn 64 windows, which looked unusable, so I invented a decision and handed it back. But the developer had already decided by picking the option, and the skill already said to list the paths and open them. The question stalled the review at the exact moment they were ready to look, and made them do my job to get what they had just asked for. The general fault is treating an awkward consequence of an instruction as grounds to re-open the instruction. If a screenshot count is genuinely unwieldy, that is a defect in how the pass captures evidence, to raise as its own ticket; it is not a question to put to the developer at the approval gate. The rule is written to bind on the count specifically ("6 or 64, open them all") because the count is what tempted the deviation, and a rule that only says "do not ask" reads as advisory the next time the number is big.

## 2026-07-17: A merge conflict parks an approved ticket in the new `conflicts/` queue instead of counting as a failure and sending it back to `todo/`

**What changed:** a new queue, `conflicts/`, holds an approved ticket whose commits will not cherry-pick onto the current main. Three rules changed with it. **A cherry-pick conflict is no longer a failure**: it is never recorded with `fail-ticket.ts` and counts toward no cap, because main moving under an approved ticket says nothing about that ticket's work. **It never returns to `todo/` or `human-review/`**: `pb:next` drains `conflicts/` **first**, ahead of `merge-queue/`, rebasing and re-verifying each ticket in its existing worktree and returning it straight to `merge-queue/` on the approval the developer already gave. **The rebase is the only change permitted** there; a failed rebase, or a check that then fails on the new main, *is* a failure, but it keeps the ticket in `conflicts/` under the cap (there is nothing to re-implement) and parks it in `blocked/` at three. `conflicts/` shares the ten-ticket in-flight budget with `todo/` and `in-progress/`, since a rebase is implementation work on the same host. No status field was added: the queue a ticket sits in remains its status, and a `conflicts/` directory plus a `status: conflict` field would be two copies of one fact that can disagree. Because a conflict ticket stays in `conflicts/` while it is worked, its queue cannot show whether a sub-agent reached it, so the end-of-turn reconciliation tracks it by **what the parent spawned** rather than by queue: a ticket whose sub-agent returned but which is still in `conflicts/` is an un-recorded failure; one no sub-agent was spawned for is simply re-driven. Encoded in `scripts/lib/move.ts`, `scripts/next-tickets.ts`, `scripts/board-tickets.ts` (plus their tests), `.claude/commands/pb/next.md`, `.claude/commands/pb/board.md`, `.claude/commands/pb/status.md`, `docs/process.md`, `handbook.md`, and `glossary.md`.

**Why:** `resource-search-2` was approved by the developer at `pb:review` (state commit `07b5895`), then conflicted while building a merge train behind two other tickets (`cd4fee8`). The old rule called that a failure: it counted as strike 2, and the ticket went back to `todo/`, the back of the entire loop. Two environmental e2e failures on an overloaded host then took it to strike 3 and into `blocked/`, needing a human to reset its count and re-admit it. Four re-drives later it arrived back in `human-review/` looking like a ticket nobody had ever seen, and the developer re-reviewed work they had already approved — including standing up a 2,000-pod cluster to explore it by hand — before discovering from the state repo's git log that the approval had happened at all. The only substantive change in all of that was the rebase, which the implement stage resolved without difficulty on the first attempt. So the loop threw away a human decision and spent days of machine time re-deriving a change that needed a rebase and nothing else. Routing the conflict to its own queue keeps the approval alive, does the one thing actually required, and never asks the developer to decide the same thing twice. The queue is drained first because every turn main drifts further from an unrebased ticket, making its next rebase worse. The developer chose "always straight to `merge-queue/`" over having agent review judge whether the rebase changed behaviour and route a changed one back for a look: `merge-queue/` is reachable only through their approval, so nothing that can conflict is unapproved, and the extra gate would reintroduce the cost this change exists to remove.

## 2026-07-16: pb:review opens a selected ticket with a concise summary card plus its human-rejection history

**What changed:** when the developer selects a ticket, `pb:review` prints two things before the inspect menu: a list of **every prior human rejection** (oldest first, each with a very brief note on how it was subsequently rectified, or `Human rejections: none.`, read from the ticket's `## History`, human "Human review: REJECTED" entries only, never agent-review rejections), then the ticket's **summary card**. The card (`scripts/ticket-card.ts`) is deliberately short: the ticket's name, a **trimmed Description** (the lead prose of `## Description`, blockquote/todo preamble stripped, cut before any `### ` subsection), **counts** for changed files (`N (code, docs)`) and screenshots (count plus the directory), the latest evidence pass, test results, test plan, commit, the `detail.md`/`evidence/` paths, and the tailored inspect menu. The full lists (every changed file, every screenshot path) are **not** printed; they live behind the inspect menu, opened on demand (option 1 lists and opens the screenshots from the card's screenshots directory; the diff options show the files). The skill drives the card through `ticket-card.ts` everywhere; the earlier mention of `format-ticket-selection.ts --card` in the skill's intro was removed, because that snapshot-backed path rendered a *different* card that silently omitted screenshots entirely. Encoded in `.claude/commands/pb/review.md`, `scripts/ticket-card.ts` + `scripts/ticket-card.test.ts`, `scripts/CLAUDE.md`, `docs/process.md`, and `handbook.md`.

**Why:** two facts most orient the review decision and were not surfaced up front: what the ticket actually is (the menu shows only a truncated one-liner) and whether it has already been human-rejected and sent back (which says a lot about what to scrutinise, and whether the rework addressed the earlier complaint). A ticket like `cluster-cache-3` had been human-rejected once already and reworked; knowing that on selection tells the reviewer exactly what to re-check. But an earlier attempt this same day to instead print the whole card **verbatim** (every changed file, all 64 screenshot paths for a ticket like `timestamp-format-1`) buried the developer in a wall of paths on selection, which is the opposite of helpful at a gate where they are deciding. The resolution is a card that is **complete at a glance but short**: the script owns the data and prints counts, so nothing is silently dropped or LLM-summarised, yet the reviewer is not overwhelmed, and every path is one keystroke away through the inspect menu. (A further improvement noted in the project todo, not done here: store the rejection history as structured data so the script can render it too, instead of the agent reading it out of History prose.)

## 2026-07-15: Each implementation pass must be self-proving, with freshly-captured evidence

**What changed:** the evidence rules now require the **latest** `evidence/implementation-N/` to hold **all** the evidence needed to prove the **entire** change on its own, and every artifact (screenshots especially) to be **captured fresh from that pass's own commit**, never copied or carried forward from an earlier `implementation-N/`. A re-implementation re-captures the whole required set into its own subdir even when its diff is a single line or touches no UI. Agent review judges the latest pass alone (no fallback to earlier passes) and rejects a latest pass whose evidence is incomplete or not freshly captured. Encoded in `.claude/commands/pb/next.md` (the "Verification and Evidence" definition, the UI-screenshots evidence bullet, the implement-step criteria, and a positive self-proving statement the agent-review step enforces), and documented in `docs/process.md` and `handbook.md` (the "one subdir per pass" definitions and the UI-screenshots hard-rejection). These process files apply to every project, so the per-project `docs/rules/testing.md` was deliberately **not** touched. The ticket card (`scripts/ticket-card.ts`) was also **left unchanged**: it already reads only the latest pass, which is now correct because that pass is required to hold all the evidence.

**Why:** `labels-modal-1` reached human review with the ticket card showing no screenshots, even though 24 existed. Its last pass (`implementation-3`) changed one doc line, recaptured nothing, and reused `implementation-2`'s screenshots, so the latest pass had none and agent review (correctly, under the old rule that scoped screenshots to the pass's own diff) passed it. Two fixes were rejected: adding a card fallback to an earlier pass would surface **stale** screenshots taken from a previous version of the code, and searching all passes still can't tell whether the newest screenshots match the current code. The durable fix is to make each pass self-proving and its evidence freshly captured, so the card can read the latest pass as the single source of truth with no fallback and no staleness. Recapture is cheap; a pass resting on a prior version's proof is not proof.

## 2026-07-14: The sandbox VM is set up and started by scripts, not by hand

**What changed:** two new bash scripts replace the hand-run command sequence for the sandbox VM. `scripts/setup-host.sh` is one-time per host: it installs Multipass and `nfs-kernel-server` and enables and persists IP forwarding. `scripts/vm.sh` is per session: it creates the VM (named after the repo directory) or starts it if stopped, exports the repo over NFS, mounts it in the VM at `/home/ubuntu/<repo>`, and opens a shell there; it also takes `up`, `shell`, `stop`, and `status`, and is tunable with `PB_VM_*` environment variables. On a VM's first launch it runs the existing `install-prereqs.sh` inside it, so a fresh machine goes from nothing to a working VM with two commands. Neither script is specific to a project: everything derives from the repo directory the script sits in. The Host + VM section of `handbook.md` (plus `README.md`, `index.md`, `scripts/CLAUDE.md`) now documents the two commands instead of the manual steps.

**Why:** starting the VM was a copy-and-paste ritual on every host reboot: start the VM, read its new IP, edit `/etc/exports` to match, re-export, shell in, re-mount. Every step of it is mechanical and every step of it was a chance to get a stale IP and a dead mount. Two decisions make the scripted version cheap to re-run: the NFS export is granted to the Multipass **bridge subnet** rather than to the VM's IP (the IP changes on every restart, the subnet does not), so `/etc/exports` is written once per repo and every later run needs no host sudo at all; and every step checks before it acts, so the common case (VM already up, already mounted) does nothing and just opens the shell. NFS rather than `multipass mount` because the loop is disk-heavy and Multipass's own mounts are several times slower (NFS 1,700 MB/s vs SSHFS 623 MB/s vs virtio-fs 195 MB/s on the machine this was measured on).

## 2026-07-10: Ticket IDs are allocated by tooling, not by hand

**What changed:** ticket IDs are now minted with `scripts/next-id.ts <prefix>`, which scans **every** queue (todo, in-progress, agent-review, human-review, merge-queue, done, backlog, blocked, aborted) and returns the next free `{prefix}-{n}` (or `{prefix}-d{n}` with `--debug`). `next-id.ts --check <id>` reports whether an explicit ID is free and exits non-zero if taken. The four ID-minting skills (`pb:add`, `pb:plan:break`, `pb:todo:break`, `pb:debug`) now call it instead of numbering by eye, and for a batch under one prefix they take the starting number once and count up locally. Fixed the misleading `pb:todo:break` example that reused `-1` IDs for features already in `done/`. The pure allocation helpers live in `next-id.ts` itself (exported, unit-tested in `next-id.test.ts`), not in `lib/`, because only that one script imports them. Added `smoke-next-id.sh` and wired it into `bun run smoke`. Also renumbered five already-created `todo/` tickets that collided with `done/`: `all-resources-1`→`-2`, `clickable-resource-rows-2`→`-3`, `cluster-cache-1`→`-2`, `live-logs-1`→`live-logs-4`, `performance-tabs-1`→`-9`, and updated the prose cross-references in `hpa-dashboard-1`, `clickable-resource-rows-1`, `live-logs-2`, `live-logs-3` to match.

**Why:** `pb:todo:break` restarted each feature's counter at 1, so a feature whose earlier tickets had already reached `done/` minted IDs that already existed there (five collisions in one run). A ticket's ID identifies it for its whole life; the queue is only its state. Uniqueness must not depend on the agent remembering to scan `done/` (it didn't) — a deterministic script that scans all queues is the guarantee, and `move()` already refuses an ambiguous or destination-colliding ID, so a stray collision now fails loudly at creation via `--check` rather than jamming the pipeline later.

## 2026-07-02: Rely on native relative-path worktrees (git >= 2.48)

**What changed:** the playbook no longer relativizes worktree link files by hand; it requires git >= 2.48 and lets git write them relative. Removed `scripts/lib/relative-worktree.ts` (`computeRelativeLinks`/`relativizeWorktree`) and the one-shot `scripts/repair-worktrees.ts`, plus their tests and `smoke-repair-worktrees.sh`. `setup-ticket.ts` and `merge-ticket.ts` now create worktrees with `git worktree add --relative-paths`, so both link files (the worktree's own `.git` and the admin back-link) are relative and survive a shared (NFS) repo mounted at different paths — previously only the worktree's `.git` was relativized and the admin back-link was kept absolute because git 2.43 required it. Added `scripts/lib/git-version.ts` (`assertGitVersion()` over `MIN_GIT_VERSION` 2.48.0, with pure `parseGitVersion`/`meetsMinimum` helpers); every CLI that touches worktrees (`setup-ticket`, `merge-ticket`, `reset-loop`, `conclude-debug`) asserts it in `main()` and fails fast on older git. `install-prereqs.sh` now installs the latest git (git-core PPA) and verifies the minimum. Also fixed the **abort** path in `pb:review`: aborting a ticket now always tears down its worktree and branch (the work is abandoned, so leaving them just orphans them); previously abort only moved the ticket to `aborted/`, which is how an orphaned `worktrees/<id>` branch was left behind. Updated smoke assertions (both link files now relative), `scripts/package.json`, `scripts/CLAUDE.md`, `README.md`, and `docs/process.md`.

**Why:** the hand-rolled relativization existed only because the installed git (2.43) predated native relative-path worktrees and its `worktree remove`/`list` rejected a relative admin back-link. git 2.48 makes relative worktrees a first-class feature, so the workaround (and its keep-the-back-link-absolute caveat) is dead weight. Requiring 2.48 and failing fast is simpler and more correct than carrying migration/repair code for a limitation that no longer applies. The abort teardown fix closes the last worktree/branch leak: merge and Debug conclusion already delete the branch, but abort did not.

## 2026-07-01: Debug tickets close their worktree on conclusion

**What changed:** a concluded Debug ticket now closes its worktree. Previously worktree teardown lived only on the merge path (`merge-ticket land`), which iterates the tickets it merges — so a ticket reaching `done/` any other way kept its worktree forever. A Debug ticket is exactly that case: agent-review sends it straight to `done/` (spawning a Fix ticket) without ever going through the merge train, so its `project/worktrees/<id>` was orphaned. Added `scripts/conclude-debug.ts <id>` (move to `done/` + close the worktree, committing the move) and extracted the shared piece both callers use: `lib/conclude-ticket.ts` `concludeTicket()` (move-to-`done/`-and-close-worktree, teardown best-effort) over `lib/worktree-teardown.ts` `removeWorktreeAndBranch()` (extracted from `merge-ticket.ts`). `merge-ticket land` now concludes each ticket through `concludeTicket()` and only separately tears down the throwaway train worktree; the old `cleanupTrain` is gone. The `pb:next` and `pb:debug` skills now conclude a proven Debug ticket with `conclude-debug.ts`, never `move.ts`. Edited: `scripts/merge-ticket.ts`, `scripts/conclude-debug.ts` (new), `scripts/lib/conclude-ticket.ts` (new), `scripts/lib/worktree-teardown.ts` (new), their tests, `scripts/smoke-conclude-debug.sh` (new), `scripts/package.json`, `scripts/CLAUDE.md`, and the `pb:next`, `pb:debug` skills.

**Why:** worktree teardown was coupled to *how* a ticket reached `done/` (the merge path) rather than to the ticket concluding, so the one terminal path that skips merge leaked a worktree every time. Giving Debug conclusion its own script, sharing the exact move-and-close step with merge, closes the leak at the point a Debug ticket concludes and keeps the two conclusion paths identical. (`move.ts` was deliberately **not** made to tear down worktrees: its job is a pure state-repo directory move, and reaching into the project repo from every move was the wrong home.)

## 2026-07-01: No docs are required in the project repo

**What changed:** the process no longer mandates any documents in `project/`. Previously the project repo "must contain" `CLAUDE.md`, `docs/spec/`, `docs/testing-manual/`, `docs/rules/`, and `docs/roadmap.md`, and bootstrap treated each missing one as a gap to fill. Now none are required: whatever docs and rules a project keeps are respected and kept current with the code, and the doc-driven-or-code-driven, fan-out-to-the-rest principle applies to whatever documentation exists. The spec/testing-manual convention (spec as source of truth, manual mirrors it, conflicts resolve in the spec's favour) is retained only *where a project keeps a spec*. Bootstrap changed accordingly: `pb:bootstrap:existing` now **assumes the project's documentation is already complete**, so it no longer analyses for or reports missing docs and queues no doc work (the only ticket it may create is one to get a failing test suite green); `pb:bootstrap:new` seeds only the starter rule set from the interview and no longer writes a spec or testing manual upfront or asks the developer which docs to adopt. Neither skill ever asks the developer to adopt a doc set. Rules in `project/CLAUDE.md` or `project/docs/rules/` are still respected and enforced by agent-review when present, but are not required. Edited: `docs/process.md`, `index.md`, `README.md`, `CLAUDE.md`, `handbook.md`, and the `pb:bootstrap:new`, `pb:bootstrap:existing`, `pb:next`, `pb:review`, `pb:todo:break`, `pb:customize`, `pb:help` skills. Templates under `templates/project/` were left as-is: the template may still ship a spec, testing manual, and rule set as an opinionated starting point.

**Why:** to decouple the Playbook from any particular project layout, so bootstrapping `project/` does not force a fixed doc set on projects that do not want one. The value (keeping docs in sync with code, either direction) is preserved without prescribing which docs must exist.

## 2026-06-25 — Removed `current-state.md`

**What the file did:** `current-state.md` was a per-project, human-readable summary that sat on top of the ticket queues at `state/current-state.md`. It had a top `⚠ Needs your action` section (blocks, broken main, environmental/setup failures, awaiting-review, run-halt and session-interrupt notes) and a `Progress` section (in-flight and recently completed tickets). It was a *derived* view: the queues were always the source of truth, and the parent agent maintained the file by hand on every queue change, committing it via `commit-state.ts`.

**Why it was removed:** the developer did not use it; the AI did not need it (the queues are the source of truth and `/pb:status` regenerates the same view live); maintaining it added a read/edit/commit to nearly every skill on every queue change, slowing the agent; and its single-committer rule (a shared-file write would race parallel sub-agents) blocked multiple AIs from using one state repo at once. Its only non-derived content (the systemic-failure-halt and session-interrupt banners) is now surfaced transiently in chat; the queues remain the durable record.
